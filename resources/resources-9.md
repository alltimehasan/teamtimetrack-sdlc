# 2. PostgreSQL extensions

Before the application tables, we'll establish the PostgreSQL capabilities we actually need.

For UUID generation, I recommend using PostgreSQL's UUIDv7 support where available in the target PostgreSQL version, rather than inventing a custom UUID implementation in every migration.

We should also verify the exact PostgreSQL version on the production VPS before finalizing this migration.

So the first migration should be something conceptually like:

```text
create_database_extensions
```

rather than immediately creating application tables.

---

# 3. Laravel UUID strategy

For Laravel models, we'll use UUID primary keys.

Conceptually:

```php
$table->uuid('id')->primary();
```

However, there's an important issue:

### Who generates the UUID?

For normal API-created records:

```text
Laravel
   ↓
generate UUID
   ↓
PostgreSQL
```

For offline Electron events:

```text
Electron
   ↓
generate client_event_id
   ↓
offline storage
   ↓
sync
   ↓
Laravel
   ↓
PostgreSQL
```

Therefore:

- Database entity IDs are generated by the application/database strategy we finalize.
- Offline event IDs must be generated by the Electron client.
- `client_event_id` provides synchronization idempotency.

We should **not** rely on auto-incrementing IDs.

# 4. Migration 01 — Users

Schema::create('users', function (Blueprint $table) {

### Important

We're using:

```php
$table->timestampsTz();
```

rather than:

```php
$table->timestamps();
```

because our physical schema uses timezone-aware timestamps.

# 10. Migration 06 — Membership Roles

Notice the cascade here.

If the **relationship** is removed, the pivot row should disappear.
