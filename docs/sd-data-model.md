# Domain & Database Design

**70 domain tables** in PostgreSQL 16. The 51 tables from the source research, plus 19 required by the product decisions and by mechanisms this design introduces.

---

## 1. Conventions

Applied without exception. Deviations are defects.

| Concern | Rule | Source |
|---|---|---|
| Primary key | `UUID`, UUIDv7 generated by the application; client-generated where offline creation is required | `ADR-006` |
| Join tables | Composite primary key of the two foreign keys — no surrogate id | `resources-8.md` §12 |
| Timestamps | `TIMESTAMPTZ`, stored as UTC, never `TIMESTAMP` | [`BR-ORG-005`](#/business-rules) |
| Dates | `DATE` for calendar concepts (attendance date, period bounds, effective dates) |  |
| Durations | `BIGINT` seconds. No floating point, ever | [`BR-PAY-008`](#/business-rules) |
| Money | `NUMERIC(12,2)` with an explicit `CHAR(3)` currency alongside | [`BR-PAY-007`](#/business-rules) |
| Status | `VARCHAR(30)` + `CHECK` constraint, mirrored by a PHP backed enum | `resources-8.md` §6 |
| Booleans | `NOT NULL DEFAULT` — never nullable |  |
| Soft delete | `deleted_at` only where historical relationships matter: users, organizations, memberships, teams, projects, tasks, schedules, office locations. **Never** on event or media tables — those are governed by retention | `resources-8.md` §49 |
| Tenant column | `organization_id UUID NOT NULL` on every tenant-owned table, leading every composite index | [`BR-ORG-001`](#/business-rules) |
| JSONB | Configuration and diagnostic payloads only. Never business fields | `resources-3.md` §48 |

### Foreign key delete behaviour

| Relationship kind | Behaviour | Reason |
|---|---|---|
| Historical / business records | `ON DELETE RESTRICT` | Removing a membership must never destroy their time, timesheets or payroll — [`BR-USER-003`](#/business-rules) |
| Pure join tables | `ON DELETE CASCADE` | An unassignment should not leave an orphan row |
| Child of an owning aggregate | `ON DELETE CASCADE` | `recording_segments` → `recording_streams` → `recordings` |
| Nullable actor references | `ON DELETE SET NULL` | `audit_logs.actor_membership_id` — system actions have no actor |

## 2. Partitioning `ADR-007`

Eight high-volume tables use **declarative range partitioning by month** on their time column, created from the first migration.

```text
tracking_events        PARTITION BY RANGE (occurred_at)
activity_events        PARTITION BY RANGE (started_at)
application_usage      PARTITION BY RANGE (started_at)
website_usage          PARTITION BY RANGE (started_at)
screenshots            PARTITION BY RANGE (captured_at)
recording_segments     PARTITION BY RANGE (created_at)
connectivity_events    PARTITION BY RANGE (occurred_at)
audit_logs             PARTITION BY RANGE (created_at)
```

:::warning This reverses the source research, deliberately
`resources-10.md` §32 recommends plain tables at MVP and partitioning later. That advice optimises for simplicity but ignores the retention requirement. Deleting hundreds of millions of expired rows with `DELETE` produces long transactions, table bloat, index bloat and sustained autovacuum pressure on a single-host deployment. `DROP TABLE partition_2026_08` is instant and reclaims the space immediately. Retention is a hard commitment (`SC-06`, 3/6/24 months), so the cheap-to-add-now, expensive-to-add-later trade favours partitioning from day one. `ADR-007`.
:::

A scheduled command maintains a rolling window: create the next three months ahead, detach and drop partitions once every organization's retention has passed for that range.

### The idempotency consequence

PostgreSQL requires a partitioned table's unique index to include the partition key. So the tracking idempotency constraint becomes:

```sql
UNIQUE (organization_id, client_event_id, occurred_at)
```

rather than `UNIQUE (organization_id, client_event_id)`.

This is exactly as strong in practice. `client_event_id` and `occurred_at` are both generated once, at the moment the event is created on the device, and are immutable in the local store. A retry always carries both unchanged. The only sequence the composite key would not catch is a client re-sending the same `client_event_id` with a *different* `occurred_at`, which is a client defect rather than a duplicate; a nightly reconciliation query detects it:

```sql
SELECT organization_id, client_event_id, count(DISTINCT occurred_at)
  FROM tracking_events
 GROUP BY 1, 2 HAVING count(DISTINCT occurred_at) > 1;
```

## 3. Time and calendar strategy

```text
Storage        every instant as TIMESTAMPTZ in UTC
Organization   timezone for presentation and default calendar boundaries
Schedule       its own timezone — a team in another country has its own schedule
Presentation   convert at the boundary, never in the database
```

Calendar-sensitive computations — attendance dates, shift windows, timesheet periods, payroll periods, report day buckets — are evaluated in the **schedule's** timezone, not the organization's, because a Schedule is what defines a working day. [`BR-SCHED-005`](#/business-rules).

An overnight shift is attributed to its **start date**. [`BR-SCHED-002`](#/business-rules). A shift whose `end_time <= start_time` crosses midnight; nothing may assume otherwise. [`BR-SCHED-001`](#/business-rules).

## 6. Work management

```text

                UNIQUE (organization_id, name) WHERE deleted_at IS NULL
```

`team_managers` is separate from `team_members` because managing a team and belonging to it are different facts — a Manager who does not appear in their own team's reports is a common and correct arrangement.

### `device_displays` — new, `DEC-032` `ADR-010`

The physical-display identity the multi-display decision requires.

| Column | Type | Notes |
|---|---|---|
| `id` | `UUID` PK | |
| `organization_id` · `device_id` | FK RESTRICT / CASCADE | |
| `display_key` | `VARCHAR(128)` | **stable physical identity** — see below |
| `os_display_id` | `VARCHAR(64)` | the OS handle at last observation; may change |
| `label` | `VARCHAR(150)` NULL | manufacturer + model where available |
| `physical_width` `physical_height` | `INTEGER` | true pixels |
| `logical_width` `logical_height` | `INTEGER` | after scaling |
| `scale_factor` | `NUMERIC(4,2)` | e.g. `1.50` |
| `rotation` | `SMALLINT` | 0 / 90 / 180 / 270 |
| `bounds_x` `bounds_y` | `INTEGER` | virtual-desktop position |
| `is_primary` | `BOOLEAN` | |
| `is_captured` | `BOOLEAN` | false when beyond the 4-display cap |
| `first_seen_at` `last_seen_at` | `TIMESTAMPTZ` | |

```sql
UNIQUE (device_id, display_key)
INDEX  (organization_id, device_id, last_seen_at)
```

**`display_key`** is derived from the most stable identifiers the platform exposes, in order of preference: EDID manufacturer + product code + serial → monitor device path → a synthetic key from `physical_width × physical_height × scale_factor × ordinal`. Display *index* is never used as identity, because unplugging a monitor renumbers the rest — `DEC-019` states this requirement explicitly.

**Cap of 4** (`DEC-025`) is enforced by the tracker, which marks displays beyond the cap `is_captured = false` and surfaces the condition to the member and in the device inventory.

### `recordings` → `recording_streams` → `recording_segments` — `ADR-011`

The three-level model the multi-display decision requires.

```text
recordings                    one per tracking session
  id · organization_id · membership_id · tracking_session_id
  · started_at · ended_at · duration_seconds
  · status VARCHAR(30) CHECK IN ('recording','uploading','processing','ready','partial','failed','deleted')
  · stream_count SMALLINT · total_size BIGINT
  · deletion_eligible_at TIMESTAMPTZ NULL
  INDEX (organization_id, membership_id, started_at)

recording_streams             one per physical display
  id · recording_id FK CASCADE · device_display_id FK RESTRICT
  · started_at · ended_at · duration_seconds
  · width · height              -- capped at 1920×1080, DEC-026
  · frame_rate SMALLINT         -- 10, DEC-026
  · container VARCHAR(20)       -- 'webm', DEC-031
  · codec_video VARCHAR(30)     -- 'vp9'
  · codec_audio VARCHAR(30) NULL
  · mime_type VARCHAR(100)      -- 'video/webm; codecs=vp9'
  · segment_count INTEGER · total_size BIGINT
  · status VARCHAR(30)
  UNIQUE (recording_id, device_display_id)
  INDEX  (recording_id)

recording_segments            partitioned by created_at
  id · recording_stream_id FK CASCADE
  · sequence INTEGER
  · started_at · ended_at TIMESTAMPTZ    -- absolute, for cross-stream alignment
  · offset_ms BIGINT                     -- from recording start, for playback seek
  · storage_key VARCHAR(1000) · duration_seconds · file_size
  · checksum VARCHAR(128) · status VARCHAR(30)
  PRIMARY KEY (id, created_at)
  UNIQUE (recording_stream_id, sequence, created_at)
  INDEX  (recording_stream_id, sequence)
```

Container and codec are **stored, not assumed** — `DEC-031` requires that MP4 remain a possible derived representation without a schema change.

`started_at` on the segment plus `offset_ms` from the recording origin is what supports the synchronised multi-display playback `DEC-019` calls for.

## 11. Timesheets and payroll

```text
timesheets           id · organization_id · membership_id
                     · period_start DATE · period_end DATE
                     · periodicity VARCHAR(20)          -- one per org, BR-TS-002
                     · total_seconds · payable_seconds
                     · status CHECK IN ('draft','submitted','approved','rejected')
                     · submitted_at · submitted_by · approved_at · rejected_at
                     · reopened_at · reopened_by · reopen_reason
                     UNIQUE (organization_id, membership_id, period_start, period_end)
                     INDEX  (organization_id, status)

timesheet_entries    id · timesheet_id CASCADE · time_entry_id RESTRICT
                     · duration_seconds BIGINT        -- SNAPSHOT, BR-TS-004
                     · project_id · task_id           -- snapshot of attribution
                     UNIQUE (timesheet_id, time_entry_id)
                     UNIQUE (time_entry_id)           -- BR-TS-003, one timesheet per entry

timesheet_approvals  id · timesheet_id CASCADE · reviewer_membership_id RESTRICT
                     · action CHECK IN ('submitted','approved','rejected','changes_requested','reopened')
                     · comment TEXT NULL
                     · is_self_approval BOOLEAN DEFAULT false      -- DEC-022
                     · created_at
                     INDEX (timesheet_id, created_at)
                     CHECK (action <> 'rejected' OR comment IS NOT NULL)
```

`UNIQUE (time_entry_id)` on `timesheet_entries` is the single structural guarantee against paying for the same work twice — it makes [`CONF-08`](#/source-audit) impossible rather than merely discouraged.

`is_self_approval` implements `DEC-022`: an Owner who is the sole active member may approve their own timesheet, and the fact is permanently visible in the approval history and the payroll export.


The rounding policy is **snapshotted onto the period**, so re-reading a processed payroll always explains itself. [`BR-PAY-004`](#/business-rules), `DEC-010`.

## 14. State machines

Enforced in the domain layer, mirrored by `CHECK` constraints and PHP enums.

```text
tracking_session   active ⇄ paused → stopped
                   any → stopped (auto_max_duration | crash_recovered | membership_suspended)

timesheet          draft → submitted → approved
                                    ↘ rejected → draft
                   approved → draft   (reopen: permissioned, reasoned, audited)

payroll_period     draft → open → calculating → calculated → approved → processed
                                 ↘ failed → calculating
                   processed → open  (reopen: supersedes entries, invalidates export)

leave_request      pending → approved | rejected | cancelled
                   approved → cancelled  (future dates only)

recording          recording → uploading → processing → ready
                                                     ↘ partial
                                        ↘ failed
                   any → deleted

screenshot         available → pending_deletion → deleted

subscription       trialing → active → past_due → active
                                    ↘ canceled → expired

capture_pause      open → ended (member) | ended (auto_resumed after 30 min)
```

**Reopening is never an edit.** Both timesheet and payroll reopen paths retain the prior record — `superseded_by` on payroll entries, an append-only `timesheet_approvals` row for timesheets. [`BR-TS-006`](#/business-rules), [`BR-PAY-005`](#/business-rules).

## 15. Invariants enforced by the database

The correctness properties that do not rely on application code being right.

| Invariant | Mechanism |
|---|---|
| One membership per user per organization | `UNIQUE (organization_id, user_id)` |
| Globally unique email | `UNIQUE (email)` |
| Idempotent event ingestion | `UNIQUE (organization_id, client_event_id, occurred_at)` |
| At most one live tracking session per member | Partial unique index |
| No overlapping time entries per member | `EXCLUDE USING gist` on `tstzrange` |
| No overlapping schedule assignments | `EXCLUDE USING gist` on `daterange` |
| No overlapping pay rate periods | `EXCLUDE USING gist` on `daterange` |
| No overlapping leave requests | `EXCLUDE USING gist`, partial on status |
| One attendance record per member per date | `UNIQUE (organization_id, membership_id, date)` |
| A time entry belongs to at most one timesheet | `UNIQUE (time_entry_id)` |
| One live subscription per organization | Partial unique index |
| One recording stream per display per recording | `UNIQUE (recording_id, device_display_id)` |
| Manual entries carry a reason | `CHECK (source <> 'manual' OR reason IS NOT NULL)` |
| Rejections carry a comment | `CHECK (action <> 'rejected' OR comment IS NOT NULL)` |
| Capture pause bounded at 30 minutes | `CHECK (duration_seconds <= 1800)` |
| Tenant isolation | Row-level security policy per tenant table |
